# ScopePilot Burp Suite Professional 代替仕様案

作成日: 2026-10-17  
更新日: 2026-10-18（TypeScript単一構成と概要設計の確定事項へ整合）
状態: 基本方針確定。機能ごとの概要設計と未達時の無効化条件は `docs/design/**` を正本とする。本改訂では、ScopePilot の目的を「許可された対象に対する脆弱性診断の自動実行」と定め、これまでの観測後限定・手動1件ずつ・能動診断の既定無効といった運用上の制約を、自動実行として最適な設計へ置き換える。安全な実行制御（許可範囲の強制、認可の記録、通信上限、証拠の追跡）は、自動スキャナを安全に運用するための設計として維持・強化する。

Windows・macOS で、Burp Suite Professional の購入を必須とせず、Web と API の診断を**自動で実行して所見まで出す**製品を目指す。利用者は対象と範囲と認可を与え、ScopePilot が探索・能動診断・結果整理・報告を一括で進める。推奨構成は TypeScript の共通コアと Electron デスクトップ UI を中心に、ZAP、Playwright、Nuclei、OAST を統合する方式とする（2.2）。

機能、継続更新、証拠保存までを代替対象とする。ただし Burp と同一の検出結果、独自エンジン、全 BApp の互換性までを「100%同等」と保証することはできない。業務上の完全代替と製品の完全互換を区別し、未対応の機能を残した段階で完全代替を名乗らない。

## 1 代替範囲と費用の条件

### 1.1 完成の定義

「業務上の100%代替」は、合意した必須業務シナリオのすべてで、Burp、有料サービス、有料 AI がなくても、入力、設定、**自動実行**、証拠確認、保存、再開、報告まで行える状態と定義する。ScopePilot の中心機能は、許可された対象への能動診断を含む診断の自動実行であり、手動操作（Repeater 等）は自動実行を補完・検証する位置づけとする。機能ごとに以下を管理する。

- 比較対象の Burp バージョンと、実際に使う機能・拡張の一覧。
- 本製品の実行手順、必要な外部環境、対応 OS、検証記録。
- 対応状態: 未実装、部分対応、外部 UI で対応、統合 UI で対応、検証済み。
- 意味や挙動が異なる点、未対応理由、代替手順、残作業。

既定の製品要件は本書の全機能とし、段階リリースはその一部を提供する。既存 BApp の実行や Burp プロジェクトの完全復元が必須の場合は、現案では完全互換を満たせない要件として扱う。必要な業務機能を別実装するか、移行要件を個別に決める。

Burp の公式ツール一覧を比較の基準とする。ZAP にも公式の対応表があるが、同じ名前の機能でも挙動が等しいとは限らない。[Burp ツール一覧](https://portswigger.net/burp/documentation/desktop/tools)、[ZAP 対応表](https://www.zaproxy.org/docs/burp-to-zap-feature-map/)

### 1.2 無料の条件

| 項目 | 要件 |
| --- | --- |
| 製品利用 | 必須機能にサブスクリプション、試用期限、件数課金を設けない |
| 診断エンジン | 有料の Burp、商用スキャナ、クラウド契約に依存しない |
| 更新 | 公開情報と利用条件を確認した OSS ルールを利用し、有料フィードを必須にしない |
| AI | 自動探索・能動診断・ルール診断・報告は AI なしで完結する。利用者が選択したAIは全作業を任意支援できるが、認可・権限・実行制御を変更しない |
| ローカル利用 | 通信記録と診断結果はローカル保存。更新サービスへ案件情報を送らない |
| 保守 | 上流確認、ルール審査、テスト、配布、問い合わせ対応の作業は残る |
| インフラ | OAST の公開到達性、独自ドメイン、サーバー、配布基盤等の費用は別に扱う |
| OS の配布 | コード署名や公証の費用は製品ライセンス料と分けて扱う |

目標は「必須ソフトウェアのライセンス料ゼロ」であり、開発・保守・インフラを含む総費用ゼロを約束しない。Apple の Developer ID による配布と公証には Developer Program の加入を含む準備が必要なので、一般配布時の予算項目に含める。[Apple Developer ID](https://developer.apple.com/developer-id/)、[Apple Developer Program](https://developer.apple.com/programs/whats-included/)

### 1.3 費用対効果の判断と範囲の限定

本案の目的はライセンス費の削減であるため、削減額と追加費用を比較してから各段階へ進む。比較では次の値を同じ期間（年単位）でそろえる。

- 削減額: Burp Suite Professional の利用者数 × 年額ライセンス。価格は判断時点の公式価格で更新する。
- 追加費用: 開発工数、上流追従・ルール審査・リリースの保守工数、OAST の公開環境、コード署名・公証、問い合わせ対応。
- 代替できない差: Burp Scanner と同一の検出結果、BApp、DOM Invader 等。これらが必須業務に残る場合は削減額から除く。

判断点は段階 A0 の終了時と各段階の完了時に置く。追加費用が削減額を継続して上回る見込みの場合は、段階を止めるか、対象機能を必須業務シナリオに必要な範囲へ縮小する。どちらを選んだかを記録する。

Burp Suite Professional にない機能は、代替の完成条件に含めない。具体的には、CVE 情報 DB との照合（5.1 の「脆弱性情報」「優先付け情報」）と、製品独自の署名付き更新基盤（5.2 の手順7、9 の組織内ミラー）が該当する。これらは「任意拡張」として分け、代替完了の判断とは別に採否を決める。

## 2 旧版 ScopePilot と構成の選択

旧版は `ScopePilot.csproj` が `net10.0-windows` と WPF を使用する Windows アプリだった。旧実装は本リポジトリから削除済みであり、ScopePilot2はソースを再利用せずTypeScriptで新規実装する。旧版の挙動は別リポジトリとfixtureから運用知識だけを継承する。

継承対象は案件管理、Origin制約、探索、document hints、HAR記録、ZAPの計画生成・実行・結果取込、証拠対応、日本語レポートの**意図と回帰シナリオ**である。class、層、UI資産は再利用せず、手動診断の統合画面と継続更新を含めて新規実装する。

### 2.1 旧版の Burp・有料サービス依存

Burp Suite Professional のライセンスとは別に、旧版 ScopePilot には次の依存があった。無料構成の完成条件は、Burp Pro だけでなく以下の依存も外した状態で判定する。

| 依存 | 旧版での用途 | 根拠 | 無料構成での扱い |
| --- | --- | --- | --- |
| Burp Suite Community 同梱の JRE | Burp 履歴 MCP（`mcp-proxy-all.jar`）を起動する `java.exe` | `Services/McpSetupService.cs`、`installer/FirstRun.html` | 実行環境パックの Java で起動するか、Burp 履歴 MCP 自体を任意機能にする。Burp の導入を初回必須手順から外す |
| Burp 履歴 MCP（GPL-3.0、別途取得） | AI 探索で Burp Proxy の履歴を参照 | `docs/PROJECTS-AND-HANDOFF.md`、`THIRD-PARTY-NOTICES.md` | 必須ではない（旧版でも Playwright と HAR へ切替可能）。移行用の任意機能として残す |
| 画面探索の AI（Codex CLI、GLM / zcode） | Web 探索モードのリンク巡回後に代表パターンを確認 | `README.md`「画面探索のAI」 | 利用者の AI 契約が前提。無料構成ではリンク巡回・Playwright 記録までを提供し、AI 確認は未実施として記録する |
| 文書を読み取る AI（Codex CLI、Claude Code CLI、GLM） | document hints の抽出、API 文書モード | `AGENTS.md`、`README.md` | 無料構成では抽出失敗と同じ扱いで探索を継続する。ローカルモデル用アダプター（7 章）を追加するまでは補助情報なしとする |
| Burp への引き渡し | Scope 正規表現、`.http`、出典付き JSON・TSV の出力 | `docs/PROJECTS-AND-HANDOFF.md`「探索後の引き渡し」 | 出力機能は残す。引き渡し先の既定を ZAP または統合 UI に変える |

この表にない依存が段階 A0 の調査で見つかった場合も、表へ追加してから完成条件を判定する。

### 2.2 Burp 代替と OS 対応

ScopePilot2は最初からTypeScript/Electronの単一構成とし、Windows専用実装を先行して後でUIを移植する二系列構成を採らない。コア、CLI、契約、adapterをUI非依存packageへ置き、同じコードをWindowsとmacOSで検証する。

- A0/A1の開発・技術検証はWindowsを主環境にして速度を優先する。
- macOSは別実装にせず同じ契約・fixtureを継続実行し、配布完了はA4 gateで判定する。
- Linuxは初期サポート範囲外であり、対応を表示しない。将来追加する場合も新しいOS capabilityと配布gateを定義する。

| 案 | 利点 | 制約 | 判断 |
| --- | --- | --- | --- |
| ZAP デスクトップをそのまま使う | 導入が早く、多くの手動・自動診断機能がある | ScopePilot の業務導線、証拠、更新管理との統合は別作業 | 早期の運用代替として有効 |
| ScopePilot に OSS エンジンを統合 | TypeScriptのコア、契約、UIで業務仕様を管理できる | エンジン差、通信制御、配布・保守を担当する必要がある | 採用 |
| プロキシとスキャナをすべて自作 | 内部構造を自由に設計できる | TLS、HTTP、ブラウザ、検出ルールの保守範囲が非常に広い | 初期案には採用しない |

ZAP はプロキシ、受動・能動診断、認証、スクリプト等を提供する。Nuclei は既知製品の脆弱性を検査するテンプレートの補完に使い、一般的な Web 診断をこれだけに置き換えない。[ZAP 機能](https://www.zaproxy.org/docs/desktop/start/features/)、[Nuclei 実行仕様](https://docs.projectdiscovery.io/opensource/nuclei/running)

## 3 必須機能

全行が完成版の要件である。「基盤」は利用する実装候補を示し、その機能が現在の ScopePilot に実装済みであることを意味しない。

| ID | 業務機能 | 必須仕様 | 基盤と主な追加作業 |
| --- | --- | --- | --- |
| F01 | 案件とスコープ | Origin・パス・操作・実行上限、ロール、担当、保存、再開 | 旧版モデルの意図を TypeScript コアへ再実装 |
| F02 | Proxy と Intercept | HTTP/HTTPS の中継、要求・応答の停止・編集・破棄、履歴検索、置換 | ZAP＋統合 UI |
| F03 | Target と Logger | サイトマップ、API 一覧、パラメーター、ロール、通信元ツールの横断表示 | 旧版の代表パターンと通信モデルの意図を再実装・拡張 |
| F04 | Repeater 相当 | 任意の採用要求の編集・送信、タブ、履歴、変数、応答比較、認証適用 | ZAP `core/action/sendRequest`＋統合 UI。standard モードでだけ動作し、Safe モードでは拒否される |
| F05 | Intruder 相当 | 挿入位置、辞書、位置の組合せ、抽出、判定、速度制御、再開、自動反復送信 | 初期版は ZAP `sendRequest` と製品側ジョブ管理で実装する。A0 fixture に失敗した runtime では公開しない。ペイロード集合は版管理し、6.1 の上限の内側で実行する |
| F06 | Decoder と Comparer | URL・HTML・Base64・hex の変換、テキスト・バイナリの差分、連続変換 | ローカルユーティリティ |
| F07 | Sequencer 相当 | トークン採取、統計解析、標本数と制約の表示、レポート | 製品側 TypeScript のローカル解析として実装。統計だけで安全と断定しない |
| F08 | ブラウザと探索 | 独立プロファイル、自動探索、認証・フォーム操作・状態遷移、リンク巡回、SPA、スクリーンショット、HAR | Playwright と旧版探索の回帰 fixture を基に再実装。能動診断の対象面を広げる自動操作を含める（許可範囲・禁止操作は適用） |
| F09 | 認証とセッション | Cookie・Bearer・Basic・API key、再ログイン、CSRF 更新、マクロ、複数ロール | 役割別の分離実行と認証状態監視を追加 |
| F10 | 受動診断 | 観測済み応答を解析し、追加の対象通信を発生させない | ZAP。取込と実際の再送を区別 |
| F11 | 能動診断 | 対象・ルール・強度・閾値・上限の選択、能動クロール（Spider 等）、進捗、停止、結果取込、自動実行 | ZAP＋共通の実行計画。認可と最終確認またはautomation grantの後は自動実行する |
| F12 | API 診断 | OpenAPI・Postman・GraphQL、JSON/XML/multipart、定義からの要求生成と自動診断 | 旧版 API 下書きの意図を再実装・拡張。未観測の要求も許可範囲内で生成・送信する。バイナリ等の未対応を解消 |
| F13 | Collaborator 相当 | OAST の DNS/HTTP 等のコールバックを記録し、要求と対応付ける | ZAP OAST または Interactsh。プロトコル別に検証 |
| F14 | WebSocket | ハンドシェイク・メッセージ記録、編集、自動再送、検索、診断 | 初期版は ZAP のページング記録と方向指定 text 送信に限定し、未対応操作を能力表で拒否する。許可 Origin と上限を適用 |
| F15 | HTTP/2 と高度な通信 | プロトコル選択、Host・接続先・SNI 等の扱い、正規化を伴わない編集経路 | Node HTTP/2の意味的編集を採用。wire忠実性が必要な操作は専用adapter追加まで未対応（設計13） |
| F16 | DOM 調査 | DOM の入力元・危険な出力先の調査、ブラウザ上の証拠、手動確認 | ブラウザ計測を追加。DOM Invader と同一能力は前提にしない |
| F17 | 認可と業務ロジック | ロール・所有者別の要求比較、期待結果、診断template、手動確認記録 | 診断項目Excelからreview済みtemplate catalogを生成。差分のみで認可不備を確定しない |
| F18 | 既知脆弱性と構成 | 製品・ライブラリ・版の根拠、既知情報との照合、実検査 | Nuclei。情報 DB との照合は任意拡張（1.3）。内部依存関係の推測を観測と区別 |
| F19 | Organizer と報告 | 要確認通信、メモ、タグ、所見、重複整理、日本語報告、再診断 | 旧版の証拠・Markdown・Word 出力の意図を再実装・拡張 |
| F20 | 拡張と独自検査 | 公開 API、隔離ワーカー、版付きルール、無効化、検証環境 | ZAP/Nuclei アダプターと製品用 API。BApp の直接実行は非互換 |
| F21 | 自動処理 | 同一コアの CLI、JSON 結果、CI、ジョブ待ち、終了理由 | GUI 専用ロジックをサービスへ分離 |

ZAP の対応表では Requester、Fuzzer、OAST 等が対応候補に挙がる。また Host Header の編集には UI 上の制約が記載されている。対応表は ZAP 画面での機能の有無を示すもので、外部から制御する API があるとは限らない。ZAP 2.17.0 の実機検証では、`sendRequest` は手動リクエストエディタ相当の送信ができるが Safe モードでは拒否された。また fuzz-beta 13.16.0 には REST API の実装がなかった（`docs/ZAP-RESEND-WORKBENCH-PROPOSAL.md` 1章）。各 adapter は概要設計で固定した最小能力を runtime bundle ごとの fixture で検証し、不合格の能力を公開しない。F15 では通常の HTTP クライアントが行う正規化を能力表に記録し、診断意図を保持できない操作を拒否する。[ZAP 対応表](https://www.zaproxy.org/docs/burp-to-zap-feature-map/)

F15 の要求解釈差・キャッシュ・並行実行、F16 の DOM 計測、F09 の複雑な SSO、F20 の既存拡張の置換は、完全代替を左右する難所とする。UI のメニューだけを実装して対応済みにしない。HTTP/3 等は必要な業務シナリオが確定した時点で互換性表に追加する。

### 3.1 自動診断に向けた方針の切り替え

本改訂で、ScopePilot の目的を診断の自動実行に定めた。これに伴い、旧版由来の参考文書（`PROJECTS-AND-HANDOFF.md`、`detection-improvement-policy.md`、`ZAP-RESEND-WORKBENCH-PROPOSAL.md`）が置いていた「観測後のみ」「手動1件ずつ」「能動診断の既定無効」等の制約は、自動実行として最適な設計へ置き換える。2026-10-17 にオーナーの決定で `AGENTS.md` を改訂し、攻撃コードを含む診断エンジンの実装を安全制御の内側で認めた。参考文書と矛盾する場合は、本仕様、`docs/design/**`、`docs/work-logs/**`、`AGENTS.md` を優先する。

置き換えの原則は次のとおり。安全側の制御（許可範囲、認可、上限、証拠）は自動化と両立させて維持し、人手を前提にした手順上の縛りだけを外す。

| 機能 | 従来の制約 | 自動実行での設計 |
| --- | --- | --- |
| F04 Repeater 相当 | 送信は1件ずつ人が確認 | 手動編集・再送として残す。自動診断の所見を人が検証する用途に位置づける |
| F05 Intruder 相当 | 一括送信・自動反復・ペイロード同梱を禁止 | 挿入位置・ペイロード集合・判定条件を指定した自動反復送信を標準機能とする。ペイロード集合は版管理し、供給元と更新手順を記録する。6.1 の上限と認可の内側で実行する |
| F08 探索 | 閲覧中心、クリック・フォーム送信を抑制 | 認証・フォーム操作・状態遷移を含む自動探索を行い、能動診断の対象面を広げる。許可範囲と禁止操作は適用する |
| F09 認証 | 人によるログインを支援 | ロール別の自動ログイン・セッション維持・再認証を標準とする。SSO/MFA は自動化できない範囲だけ人手に切り替える |
| F11 能動診断 | 観測済み URL のみ、Spider・Requestor を使わない | 自動探索の結果に加えて、能動的なクロール（Spider 等）で対象面を広げてから能動診断を回す。既定で有効 |
| F12 API 診断 | 観測応答のない要求を送らない | OpenAPI・Postman・GraphQL の定義から要求を生成し、未観測でも許可範囲内で自動送信・診断する |
| F13・F18・F20 | ZAP / Burp の設定・連携の改善に限る | OAST、Nuclei による既知脆弱性検査、独自検査ルールを診断の構成要素として統合する |
| F14 WebSocket | 記録ブラウザーでブロック | 記録・自動再送・診断の対象に含める。許可 Origin と上限を適用する |
| 6.1 既定値 | 能動診断・Fuzzer は既定無効、実行ごとに `ACTIVE` 入力 | 案件認可とplan hashの最終確認またはautomation grantが揃えば、能動診断を含む計画を自動実行する（6.1） |

変更しないのは次の点である。これらは自動化の有無にかかわらず維持する。

- 許可範囲（scheme・host・port・パス・操作・接続先）の強制と、範囲外通信・別 Origin への認証情報転送の拒否（6.1）。
- 案件全体で共有する通信上限と、過負荷・認証切れ・証拠保存失敗の検知による停止（6.1）。
- 実行対象・範囲・認可の記録、証拠の追跡可能性、秘密値のマスク、所見を「実影響未確認」と「確認済み」で区別する表示（6.3）。
- 対象が利用者に認可されたものであることを前提とし、認可の範囲を ScopePilot が勝手に広げないこと。

## 4 共通アーキテクチャと OS 対応

### 4.1 推奨構成

UIはElectron main/preloadとReact renderer、コアとCLIはNode上のTypeScriptで構築する。ブラウザ操作はPlaywrightをTypeScriptから直接呼び、ZAP（Java）とNuclei（Go）だけを外部binaryとしてadapterの背後へ置く。UIとコアはOpenAPI/JSON Schema契約で分離し、rendererから任意のNode/Electron APIへ到達させない。詳細は[設計01](design/01-architecture.md)を正本とする。

```text
Electron renderer ─ typed IPC ─ ApplicationService ─ TypeScript core
CLI ────────────────────────────┘       ├─ SQLite + evidence files
                                       ├─ Playwright Adapter (TS API)
                                       ├─ ZAP Adapter ─ ZAP/Java
                                       ├─ Nuclei Adapter ─ nuclei
                                       └─ OAST / OS Platform Adapters
```

- ZAP は別プロセスとして API / Automation Framework 経由で利用する。API のない機能（Fuzzer 等）は「外部 UI で対応」と表示するか製品側で実装し、どちらにしたかをエンジンの能力情報に反映する。
- PlaywrightはTypeScript APIから直接利用し、旧版のNode workerを再利用しない。
- Nuclei は任意導入のワーカーとし、JSONL と実行記録を取り込む。F18 の完全提供時は検証済み構成を提供する。
- renderer内部連携は型付きElectron IPC、CLIはApplicationServiceの直接呼出し、外部Product APIは既定無効のloopbackと分離する。
- エンジンごとの能力を問い合わせ、未対応操作を実行前に拒否する。別エンジンへの暗黙の切替をしない。
- Java・Node.js・ブラウザ・エンジンを版管理した実行環境パックとして提供する。初回取得型とオフライン一括パックを用意する。Docker と WSL は必須にしない。

### 4.2 初期サポート

| OS | 検証対象 | 配布 |
| --- | --- | --- |
| Windows | Windows 11 x64 | インストーラー、portable ZIP |
| macOS | macOS 15以降のApple Silicon。IntelはElectron/Playwright/ZAPの共通サポートが維持されるreleaseだけ別capability | arm64 app/DMG、対象releaseに限りx64 app/DMG |

Node/Electron、Java、ZAP、Playwrightの共通対応範囲をreleaseごとに固定する。Linux、Windows arm64、macOS Intelを包括的に対応とは表示せず、表にない組合せは`Unsupported`とする。

### 4.3 プラットフォーム境界

| 能力 | 分離先と要件 |
| --- | --- |
| Clipboard、ファイル選択、外部link | Electron mainの許可list付きPlatform Service。rendererへ汎用APIを出さない |
| 秘密値保護 | Windows DPAPI/Credential Manager、macOS Keychain。利用不可時は平文へ降格せず都度入力 |
| テーマ、通知、window | Electron/OS adapter。coreへ型を漏らさない |
| Java、ZAP、Nuclei、browserの起動 | runtime bundleから絶対pathと引数配列で起動し、shell文字列を使わない |
| Word出力 | TypeScript `docx`で生成し、Word本体やOS固有automationを要求しない |
| 子プロセス終了とブラウザ管理 | Windows と Unix でプロセスツリーを停止。アプリ異常終了も回収する |

案件の移動では相対パスと共通形式を使う。OS の鍵ストアに結び付いた秘密値はコピーだけで移行できないため、再認証または利用者が選ぶ暗号化エクスポートで扱う。

## 5 脆弱性情報と検出ルールの継続更新

### 5.1 更新対象を分ける

| 更新対象 | 内容 | 主な供給元 | 製品の扱い |
| --- | --- | --- | --- |
| 汎用検出ルール | SQLi、XSS、設定不備等の検査方法 | ZAP のリリース品質 add-on | 安定チャンネルの中心 |
| 製品別テンプレート | 既知製品・CVE の具体的検査 | Nuclei 公式 templates | 審査済み ID とファイル集合に限定 |
| 脆弱性情報 | CVE、影響条件、更新版、出典 | CVE List V5、OSV。NVD は補完候補 | 任意拡張（1.3）。採用時は情報レコードとして保持し、実検査結果と分離 |
| 優先付け情報 | 実悪用が確認された CVE | CISA KEV | 任意拡張（1.3）。採用時は調査の優先付けに使い、対象が脆弱である証拠にはしない |
| 解説と対応表 | 日本語説明、修正方針、CWE、診断項目 | 製品管理の辞書と原典 | 検出ルールの版とは別に追跡 |
| 実行環境 | アプリ、エンジン、Java、Node.js、Chromium | 各公式配布 | 互換性・セキュリティ修正を含めて管理 |

CVE List V5 は公式 CVE レコードの取得元であり、OSV はパッケージの版やコミットに基づく照会を提供する。どちらも、情報を取り込むだけで任意の Web アプリの脆弱性が検出できるようになるものではない。[CVE List V5](https://github.com/CVEProject/cvelistV5)、[OSV API](https://google.github.io/osv.dev/api/)、[CISA KEV データ](https://github.com/cisagov/kev-data)

照合ではパッケージのエコシステム、名前、版、版の取得根拠を保持する。バナー、URL、ファイル名だけによる推定は候補とし、ライブラリ同梱・影響版該当・実際の到達性を区別する。CVE のない汎用不備も別に検出・管理する。

関連する脆弱性ごとに「情報のみ」「検査ルールなし」「ルール審査中」「検査可能」「当該実行で検査済み」を区別する。情報の同期成功を検出対応済みと表示しない。新規の重要情報は次回の更新確認で取り込み、検査ルールの審査と提供時期は別に管理する。すべての CVE に検査ルールを用意できるという保証は置かない。

### 5.2 更新の手順

A1ではエンジンとルールの版をアプリのリリースで固定し、検証済みbundle単位で入れ替える。以下の手順のうち、手順7の製品独自の署名付きマニフェストと、9章の組織内ミラーは任意拡張（1.3）とする。採用しない場合も、手順1〜6・8の確認と実行時の版固定はリリース作業で行う。

1. 起動時と稼働中は原則24時間ごとに更新メタデータを確認する。自動確認を停止し、手動・オフライン運用へ切り替えられる。
2. 公式の供給元から隔離領域へ取得する。大量の情報 DB は差分同期・キャッシュを使い、各 API の制限、ページング、再試行条件に従う。
3. 出典、供給元の更新日時、取得日時、版または commit、ライセンス、互換エンジン、ファイル一覧と SHA-256 を記録する。
4. 署名・信頼する鍵・配布メタデータを検証する。SHA-256 単独では供給元の真正性を証明できない。上流の検証手段が足りない部品は、管理者が取得・審査した製品側の署名付きパックから供給する。
5. 構文、互換性、禁止プロトコル、ファイル参照、要求数、操作、スコープ逸脱、結果形式の検査を行う。
6. ローカルの検証用 HTTP サーバーと正常・異常応答の fixture で回帰確認する。実案件を更新検査に使わない。
7. 検証済みの組合せを署名付きマニフェストにまとめ、安定チャンネルへ昇格する。新規・変更ルールは審査を経て次の実行から有効化する。
8. 実行開始時にルール、エンジン、設定の組合せを固定する。診断途中では更新しない。失敗時は直前の検証済み組合せを保持し、利用者が切り戻せる。

更新の自動化には情報収集と機械検査を含めるが、ルールが新たに発生させる通信や操作の審査を省略しない。上流の新機能に対応できない間は該当ルールを保留し、その理由を表示する。製品側の更新担当者は、上流変更の確認、昇格、失効、鍵の管理を担当する。

ZAP の release / beta / alpha の区分を UI と実行記録へ残す。Nuclei はテンプレート自動取得機能を持つため、製品からの診断実行ではエンジン独自の自動更新を停止し、製品が固定したローカル集合だけを使用する。[ZAP add-on 品質](https://www.zaproxy.org/docs/desktop/start/features/addons/)、[Nuclei 更新仕様](https://docs.projectdiscovery.io/opensource/nuclei/running)

### 5.3 ルールの信頼性と実行制限

- 安定版は検証済み release ルールと審査済みテンプレートを使う。beta / alpha / 利用者作成ルールは別チャンネルとする。
- 署名済みでも対象の変更や過負荷が起きないとは限らない。署名の検証と操作の審査を別に行う。
- Nuclei の `code`、任意 JavaScript、ローカルファイル参照、任意ネットワーク、headless、workflow 等は初期の許可対象から外す。後から追加する場合も能力単位で検証する。
- 公式テンプレートの署名を検証するとともに、補助ファイルを含む集合全体を製品のマニフェストで固定する。Nuclei の署名では一部の payload ファイル参照が digest の対象外になるため、テンプレート単体の署名だけに依存しない。
- CVE 情報から実行可能なルールや攻撃コードを自動生成し、そのまま配布・実行する経路は設けない。
- 上流で取り下げられたルール、誤検出修正、CVE の撤回・影響範囲修正を同期する。過去の結果は原本を保持し、新版での再評価を別の記録として残す。

Nuclei の署名仕様は真正性・改変検知を提供するが、すべてのプロトコルで署名が強制されるわけではない。製品側では許可する署名者とファイル集合を明示する。[Nuclei テンプレート署名](https://docs.projectdiscovery.io/templates/reference/template-signing)

### 5.4 更新状況の表示とオフライン利用

「最新」の一語で状態を表示せず、供給元ごとに、最終確認、最終成功、供給元の版、審査済み版、使用中の版、保留件数、失敗理由を表示する。同期済みでも上流の情報が完全であるとは表現しない。

初期案では最終成功から7日で注意、30日で古い情報として目立たせる。閾値は変更可能とし、オフライン指定時も経過日数を残す。これは製品の通知規則であり、脆弱性対応の保証期間ではない。

インターネットへ接続できる別端末で取得した署名付き更新パックを読み込める。改ざん・署名不一致・互換性不一致・意図しない旧版への差し戻しを拒否し、明示的な切り戻しは履歴へ残す。鍵のローテーションと失効を扱う。更新用通信は案件通信と分離し、案件 URL、Cookie、文書、所見を含めない。OSV 等へのオンライン照会を選ぶ場合も送信するパッケージ情報を明示し、機密構成ではローカル DB を使う。

## 6 実行と証拠の仕様

### 6.1 計画と通信の制御

実行前に対象、対象role、操作者、操作区分、template、エンジン、ルール、上限、想定する通信と未算定部分を計画として確定する。単純なメソッド判定で読み取り操作と決めず、GET による削除なども禁止操作として扱う。案件の認可（対象・範囲・許可した操作区分・認可者・日時）が記録されていても、desktopでは同じplan hashの実行前最終確認を要求する。非対話CLI/CIは期限・操作者・許可command・上限・計画生成条件を固定したautomation grantを必要とする。認可の範囲や操作者権限を超える対象・操作は計画生成の時点で除外し、実行時にも拒否する。認可の記録、最終確認またはautomation grant、承認証跡を自動実行でも作成・保存する。

許可範囲は scheme、host、port、パス、操作、接続先の条件を検査する。リダイレクト、DNS の解決結果、IPv6、別ホストへの認証情報転送も制御対象とする。認証に必要な外部 IdP へのアクセスは認証専用の別ポリシーとし、診断対象 Origin を暗黙に広げない。

上限はエンジン単位に加えて案件全体で共有し、要求数、Origin ごとの速度、同時接続、ページ数、実行時間、応答容量を制御する。429・5xx の増加、認証切れ、エンジン停止、証拠保存失敗を検知して一時停止または終了する。停止時に新規通信を止め、送信済み要求は取り消せないことを記録する。

入力 URL の検査だけでは外部エンジンの全通信を制限できない。通常の HTTP は管理する送信経路で検査し、直接通信を行う機能は、信頼するアダプターと必要な OS の通信制限まで検証する。HTTP/2 の特殊操作や OAST は別経路の能力として管理する。共通制約を強制できない能力は有効化しない。loopback 制限やプロセス分離だけで任意拡張を安全に実行できるとは扱わない。

### 6.2 認証と OAST

認証情報はロールと対象範囲を持ち、実行中の認証状態を確認する。ロールごとにブラウザと Cookie を分離し、失効・再認証後も要求と結果の対応を追えるようにする。SSO/MFA は人によるログインを支援し、無条件の完全自動化を完成条件にしない。mTLS や企業プロキシは必要な案件で再現シナリオを定める。

OAST は独立した機能として、管理するサーバーまたは利用者指定サーバーを優先する。公開サービスへの自動接続は無効とし、使う場合は送信情報と保存条件を示す。DNS/HTTP 等の対応、認証、保持期間、実行後の待機時間、遅延通知、要求ごとの識別子を管理する。識別子に案件名や秘密値を埋め込まない。

ZAP は OAST add-on を提供し、Interactsh も自己ホストできる。外部から対象サーバーの通信が到達できない環境では OAST を未実施とする。受信がないことを脆弱性なしの証拠にはしない。[ZAP OAST](https://www.zaproxy.org/docs/desktop/addons/oast-support/)、[Interactsh](https://docs.projectdiscovery.io/opensource/interactsh/overview)

### 6.3 保存モデル

SQLite は索引・状態・関係を管理し、大きい本文と証拠はファイルで保管する。画面では案件、エンドポイント、通信、ロール、診断計画、ジョブ、ルール、所見、証拠を相互に辿れるようにする。

- 実行記録: ID、開始・終了と理由、計画 hash、ポリシー、上限、エンジンとルールの版・hash、更新情報のスナップショット。
- 通信: 元ツール、日時、接続先、プロトコル、要求・応答、対応するロール、加工の有無。原文と表示用整形を分離し、取得できない wire 情報を推測で補わない。
- 所見: ルール ID と版、対象・パラメーター、重大度、確信度、証拠、CWE/CVE、出典、確認状態。
- 確認状態: 未確認、調査中、確認済み、誤検出、受容、修正確認。スキャナ警告と人の確認結果を分ける。
- 実施範囲: 対象と検査項目の組に、実施済み、非該当、未対応、禁止、認証失敗、時間切れ、エラーを保存する。終了コード0や警告0件だけで診断完了にしない。

Cookie・Authorization・本文に秘密値が含まれる通信原本は保護する。共有用エクスポートはマスキングした派生物とし、原本の参照と hash を保持する。証拠保管の暗号化、保持期間、容量上限、削除、バックアップ、復旧を提供する。案件全体を別 OS に移す場合はスキーマ移行前のバックアップを作成し、同時書込みを防ぐ。

### 6.4 証明書とブラウザの管理

HTTPS の中継に使う CA 証明書は利用環境ごとに生成し、秘密鍵を配布物へ共通鍵として同梱しない。証明書の指紋、有効期限、保管先、更新、削除、持出しの手順を提供する。秘密鍵は保護して保存し、共有用の案件出力には含めない。

既定は探索用の独立ブラウザと必要な範囲での証明書信頼を使う。OS や一般ブラウザの信頼ストアへ登録する場合は、利用者が変更先を選んで実行し、解除手順も提供する。対象サーバーの証明書検証を無条件で無効にせず、例外は対象と期間を限定して記録する。証明書 pinning 等で中継できない通信を欠落として表示する。

### 6.5 応答性と障害復旧

通信履歴はページング・仮想化・本文の遅延読込を使い、解析とディスク操作を UI スレッドから分離する。段階 A0 で基準端末を固定し、10万件の通信索引での閲覧・検索と、大きい応答本文の保存上限を検証対象にする。全件をメモリに保持する実装は採用しない。

実行中のクラッシュ後は完了扱いにせず、中断位置と保存済み証拠を復旧する。要求の再送を伴うジョブは自動再開せず、二重実行を防いだ再開計画を作る。エンジン停止と更新失敗が、他の案件のデータや利用者が別に起動したプロセスへ影響しないことを確認する。

## 7 文書と AI の扱い

文書を設定した Web 探索では `AGENTS.md` の document hints 方針を維持する。文書由来 URL は許可 Origin 内の探索開始点になり得るが、観測済み通信や確定所見にはしない。秘密値は派生成果物へ複写せず、文書に埋め込まれた指示には従わない。抽出失敗時は記録して探索を継続し、次回再抽出する。

有料 AI なしでも自動探索・能動診断・ルール診断・所見作成・報告を実行できるようにする。診断の自動実行は AI に依存しない。一方、利用者が選択した zcode、Claude、Codex 等のAIを、案件設定、ガイドライン理解、文書抽出、探索、対象選定、template選択、request作成支援、観測整理、所見・報告下書きの全作業で利用できるようにする。provider/model、送信範囲、redaction、提案の採否を記録し、ローカルproviderも選択できるようにする。有料 AI の設定を無料構成の初回必須手順にしない。

自動探索・自動診断では、AI の有無にかかわらず許可範囲・禁止操作・上限・認可・操作者権限を実行制御として強制する。AI出力は提案であり、AIにはこれらの制御、確認状態、所見確定を変更する権限を与えない。AI提案を採用するときは通常のcommandとしてschema validation、計画hash更新、実行前確認を行う。AIへ送る案件情報はtaskごとに最小化し、秘密値を除き、外部egressとして送信先・保存条件を明示する。

## 8 UI と移行

UIは同じ契約とcoreを使うSimple / Advancedの2モードを持つ。モードは操作の露出範囲であり、操作者権限、案件認可、scope、上限を付与・緩和しない。対象アプリのroleとScopePilot操作者を別に表示・記録する。

Simpleは「ガイドライン選択→自動クローリング→探索後の対象選定→リクエスト実行前の最終確認→実行→結果」のguided flowとし、利用者が変更できる診断操作をガイドライン、代表対象、最終確認に限定する。任意URL、payload、request、engine設定は編集できない。不足入力やSimple非対応操作は暗黙に実行せず、理由とAdvancedへの導線を示す。

Advancedは操作者が持つ権限の範囲で、ガイドライン、クローリング、対象、実行内容、判定、上限を編集できる。ZAP単体で実現できないrequestは、`docs/WebAppPentestGuidelines_診断項目_ScopePilot_作業用.xlsx`から版付きcatalogへ変換しreviewしたtemplateをガイドライン項目から選び、管理HTTP client、ZAP手動request、検証済み外部toolへ計画化する。Excelをruntimeで直接実行せず、source hash・sheet・row・importer版を保持する。

主な画面は、案件とスコープ、ブラウザと通信、リクエスト編集、Fuzzer、診断ジョブ、所見と証拠、レポート、更新と実行環境に分ける。任意の通信から再送・比較・採用・診断・メモへ移動でき、操作時にはmode、操作者、対象範囲、target roleを確認できる。

既存の ScopePilot 案件は読み込み時に版を確認し、バックアップして移行する。Burp からの移行は、利用できる形式を確認したうえで HTTP メッセージ、HAR、所見、設定の対応表を定める。`.burp` の直接読込、拡張の内部状態、タブや画面の完全復元を前提にしない。BChecks 等もそのまま動作するとは扱わず、必要な検査ごとに意味と再現条件を評価する。

現在の Burp 連携は移行用の任意機能として残せるが、通常動作の必須依存にしない。外部 ZAP UI への遷移だけで提供する機能は、その状態を明示し、統合 UI 完了と区別する。

## 9 配布と継続保守

ScopePilot 本体の BSD-3-Clause 方針を維持する。ZAP 本体は Apache-2.0、Nuclei 本体と公式 templates は MIT の公開ライセンスを確認できるが、同梱する正確な版、add-on、Java 配布物、Chromium 等は部品ごとに確認する。情報 DB の利用条件もソフトウェアのライセンスと分ける。[ZAP LICENSE](https://github.com/zaproxy/zaproxy/blob/main/LICENSE)、[Nuclei LICENSE](https://raw.githubusercontent.com/projectdiscovery/nuclei/dev/LICENSE.md)、[templates LICENSE](https://raw.githubusercontent.com/projectdiscovery/nuclei-templates/main/LICENSE.md)

配布物と実行環境パックには、部品一覧、SBOM、ライセンス・NOTICE、取得元、版、hash、更新手順を含める。既存の `THIRD-PARTY-NOTICES.md` は、実際に同梱する段階で更新する。最新の main/dev ブランチの表示を、将来の配布版の条件として固定しない。

署名付き更新パックを採用する場合（任意拡張、1.3）、配布方式には公式配布先の定期参照と、組織内ミラーの双方を用意する。独自クラウドを常時必須にしない。更新用の署名鍵はランタイムやリポジトリに秘密鍵として同梱しない。更新署名と OS が認識するアプリ署名・公証を別の仕組みとして管理する。

## 10 段階実装と完成条件

単一のTypeScript/Electron構成をA0〜A4で段階実装する。Windowsを主開発環境とするが、macOSを別系列・別UIにしない（2.2）。

| 段階 | 提供内容 | 完了条件 |
| --- | --- | --- |
| A0 技術検証 | TypeScript simulation harness、ZAP API、`sendRequest`とstandard境界、Fuzzer基準経路、自動探索→能動診断→所見、HTTP/2能力表、停止・復旧 | Windowsでfixtureを自動完走し、経路別Enforced/Delegated/Unsupportedと実測overshootを記録 |
| A1 自動診断の中核 | 案件・認可、Simple guided flow、自動探索（認証・フォーム含む）、能動診断、Fuzzer、所見、証拠、CLI | Burp、有料 AI、2.1 の依存なしで、認可・最終確認済み対象の能動診断を自動実行し所見を出せる。エンジン、catalog、ルールの版はリリースで固定し、切戻しできる |
| A2 手動診断と補完 | Proxy、Target、Repeater、変換、比較、Nuclei、DOCX報告 | 自動診断の所見を同じ認可・上限・証拠モデルで再送・比較できる |
| A3 高度な診断 | OAST、WebSocket、Sequencer、DOM、HTTP/2、API 拡充、拡張 API | 必須シナリオごとに能力と制約を検証。残る差を対応表へ反映 |
| A4 業務移行・配布 | 必要な拡張の代替、案件移行、Windows/macOS配布、署名・公証、復旧 | 両OSで必須workflowを検証し、未対応能力を公開せず、配布・rollback手順が揃う |
| 任意拡張 | 製品独自の署名付き更新パック、組織内ミラー、CVE 情報 DB の照合 | 1.3 の判断で採用した場合だけ実施する。代替完了の条件にしない |

全機能の独自再実装よりも、同じ証拠・ロール・スコープを持って複数機能間を移動できることを優先する。工期と人数はA0でエンジンAPIと通信経路の実測後に見積もる。100%を先に固定金額や短期工数へ置き換えない。

### 10.1 検証の受け入れ基準

- 公称する OS・CPU ごとに、導入、起動、HTTPS 記録、認証、再送、保存・復旧、終了、更新を確認する。
- 許可範囲外の接続・リダイレクト、秘密値の別 Origin 転送、上限超過を拒否する。複数エンジンの並行実行でも案件上限を共有する。
- 認可済み対象で、探索から能動診断、所見出力までが自動で完走する。認可の記録・承認証跡・証拠が対応して残る。
- 認可のない対象、または許可範囲外の対象・操作では、自動実行が計画生成と実行の両方で拒否される。
- Simple / Advancedが同じ計画・証拠schemaを使い、Simpleから非公開操作へ到達できず、Advancedも操作者権限を越えない。
- 診断項目Excelのsource座標から実行template、計画、通信、結果、coverageまで追跡できる。
- AI providerの有無にかかわらずworkflowが完走し、AI提案が認可・権限・最終確認を迂回しない。
- 正常・異常の fixture に対して採用ルールの期待動作と誤検出抑制を確認する。未知の対象すべてに同一の検出率を保証する基準にはしない。
- 破損パック、署名不一致、依存ファイルの改変、互換性不一致、更新先停止に対して、既存の検証済み環境と証拠を保持する。
- 診断途中の更新、異常終了、認証切れ、ディスク不足、キャンセル、OAST の遅延到着を扱える。
- 文書の記載、構成推定、情報 DB の照合、スキャナ警告、人の確認結果を UI と報告で区別する。
- 日本語表示と Word 出力を各 OS で確認し、通信原本を共有用出力へ無条件で含めない。
- DVWA 等は探索・証拠・連携・取込のワークフロー確認に使用できる。検出率のベンチマークと仕込まれた脆弱性の全検出は、明示的に合意した場合だけ実施する。

### 10.2 設計上の確定事項と実装入力

構成、画面領域、共通モデル、adapter境界、安全既定、未達時の無効化条件は`AGENTS.md`と
`docs/design/00〜27`で確定した。実装はTypeScript simulation harnessを先行し、WindowsでA0/A1を進めながら
同じ契約をmacOSで検証する。F02/F04/F05/F15の版依存挙動は設計選択ではなくcapability fixtureの測定対象であり、
未達能力は公開しない。

次は設計を変更せず、プロジェクト入力として管理する。

1. 必須業務シナリオと置換対象拡張の優先順位。未提示時はF01〜F21の要求matrix順で実装する。
2. 費用比較の利用者数、判断時点の公式価格、保守工数。値がなくてもA0の技術fixtureは進められる。
