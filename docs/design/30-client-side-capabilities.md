# 30. クライアント側 (ブラウザ・フロントエンド) 起点の診断能力要件

- 背景: ベンチマーク測定 (`docs/benchmark/juice-shop-coverage.md`) で、SPA の server 側経路は
  探索・診断候補化できても、**ブラウザ実行・フロントエンド資産でしか確認できない脆弱性**は
  現行機能の対象外だった (client-side challenge 13 件)。本章はその能力要件を製品機能として定義する。
- 原則は他章と同じ: 観測事実と根拠を明示し、対象の許可 Origin 内の資産だけを解析する。
  対象サイトのスクリプト・依存情報は「対象が配布したもの」であり、解析は受動的 (追加送信を
  伴わない) に行う。第三者サービス (脆弱性データベース) への照会は設定時のみとし、対象の
  情報 (URL・識別子) を送らない形式 (名前・版のみの照会、またはローカル DB) を使う。

## 30.1 実行検証 (browser-dom トラックの拡張)

- 対象: 反射系 XSS 所見・DOM 内の危険な取り込み (`innerHTML` 等) を持つ経路。
- 要件: payload 付き URL を隔離 browser で開き、dialog 発火・page error を「実行根拠」として
  記録する。検証 URL は scope 強制 (送信前拒否) の内側で、結果は証跡へ保存する。
- 状態 (2026-11-05 深夜): `verifyFindingExecution` (service) + `verifyPayloadExecution` (explorer) に
  加え、通常診断 (`runActiveScan`) の所見取込後に反射系 XSS 所見 (URL に payload 印字あり・上限 5 件)
  を自動検証し `ActiveScanRunResult.payloadVerifications` へ載せる接続を実装済み。UI (wizard)
  のサマリ表示にも接続済み。

## 30.2 フロントエンド依存の静的解析 (supply chain)

- 対象: 対象サイトが配布する JavaScript bundle および依存ライブラリ。
- 要件:
  1. bundle から依存名・版の申告 (コメント・sourcemap・既知の framework signature) を抽出する。
  2. 依存名の typosquatting (正当名称との編集距離) を検出する。
  3. 抽出した依存の静的シグネチャ (既知の脆弱な API 呼出パターン) を検査する。
- 判定は「bundle 中の観測」であり、datastore 系の照会結果と区別して表示する。

## 30.3 コンポーネント脆弱性データベース照合

- 対象: 30.2 で抽出した依存名・版、および応答 header の生成物シグネチャ (Server・X-Powered-By)。
- 要件: 審査済みの脆弱性データベース (OSV/CVE のローカルキャッシュ等) と名前・版で照合し、
  該当を所見化する。対象の URL・識別子を外部へ送らない (名前・版のみ、または完全ローカル)。
- 既存の Nuclei テンプレート manifest (版管理・hash 固定) と同じ供給元管理の規律を適用する。

## 30.4 暗号素材・JWT 検査 (cryptography-review トラックの拡張)

- 対象: 認証で使われる JWT (login 実行時に隔離 browser 内で観測)、公開鍵・証明書・暗号素材。
- 要件:
  1. JWT の header・署名アルゴリズムを検査し、`alg: none`・鍵混乱などの弱い構成を検出する。
  2. 署名検証を試み (対象が配布した公開鍵・既知の弱い鍵との照合)、改竄 token の受理を確認する。
  3. 公開鍵ファイル (許可 Origin 内の静的資産) の鍵長・アルゴリズムを検査する。
- 秘密値は観測結果・証跡へ出さない (既存の login 実行と同じ規律)。

## 30.5 公開面の機密漏洩検知

- 対象: 許可 Origin 内の静的資産・公開 API 応答。
- 要件: 既知の機密パターン (API 鍵・秘密鍵・トークン形式) を公開面の走査結果から検出する。
  検出は「公開されている」という観測事実に基づき、公開範囲の外へ置かれた秘密の探索は行わない。

## 30.6 优先順位と段階

1. 30.1 の所見→検証接続 (既存機能の完成) — 反射系の検出確認を伸ばす。
2. 30.3 のローカル DB 照合 — 対象の送信なしで完結するため安全性が高い。
3. 30.2 の依存抽出・typosquatting — bundle 解析の精度検証を要する。
4. 30.4 / 30.5 — 専用の検査器実装を要する。

## 30.7 測定との対応

- `docs/benchmark/juice-shop-coverage.md` の client-side 13 件 (Vulnerable Components に集中) が
  この章の能力でカバーされる想定。実装後に同表の「検出確認済み」を更新して有効性を測定する。
