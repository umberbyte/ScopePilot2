# 29 診断報告書テンプレート v2

## 1. 目的

ScopePilot2 の診断結果を、意思決定者・開発担当者・再診断担当者が同じ事実モデルから読める
日本語の DOCX / JSON / Markdown として出力する。

他社報告書は、必要な情報の種類と粒度を把握するための参考資料に限定する。章順、文言、配色、
表組み、見出し体系、図版は転用せず、ScopePilot2 独自の情報設計と視覚設計を採用する。

## 2. 設計原則

- 正規データ: `ReportModel` を機械判定結果の唯一の入力とし、レンダラーから独立させる。
- 編集データ: 顧客名、承認者、総括などは `ReportProfile` に分離し、案件単位で再利用する。
- 派生データ: `AssuranceReportDocument` を DOCX と構造化 JSON の共通モデルとする。
- 判定分離: 深刻度、確認状態、信頼度を別項目として表示する。
- 範囲の明示: 許可対象、除外対象、ロール、送信上限、禁止操作、制約を必ず記載する。
- 証跡掲載: 各指摘に診断時の Request / Response を、再現に必要な Cookie・token を含めて直接掲載する。証跡 ID と
  SHA-256 は原本の完全性確認にだけ使用し、ファイル参照を通信内容の代替にしない。
- 個別説明: 指摘ごとに脆弱性固有の概要・成立条件・正確な対象 URL と Request・確認結果・具体的な
  恒久対策・修正確認条件を記載し、一般的な定型文だけで済ませない。レスポンスヘッダの欠落が根拠なら、
  欠落したヘッダ名を明記する。
- 原因分析: 診断時通信から確認できた事実と、実装・設定・制御フローについて推定した原因を分離して
  記載する。推定原因は脆弱性種別に応じた具体的な不備候補を複数含め、ソースコードや設定を直接確認して
  いない場合は断定しない。
- AI支援: 選択されたAIは概要、成立条件、再現手順、恒久対策、修正確認条件の文章案を作成できる。
  原因分析も提案できる。finding ID と観測済み URL を検証し、必須項目や具体性が不足する場合は
  決定論的な文章へ戻す。
- 証跡の可読性: 診断入力、観測根拠、パラメータなどから着目語を導出し、DOCX の該当箇所を
  黄色で強調する。長大な Body は関連箇所の前後だけを掲載でき、省略文字数と原本保管を明示する。
- 不完全性の明示: 未実施、判定保留、推定、外部エンジン委譲を安全性の証明として扱わない。

## 3. 情報構造

テンプレート識別子は `scopepilot2-assurance-ja-v2`、構造化形式の版は `2` とする。

1. 文書管理
   - 報告書 ID、版、状態、機密区分、作成・確認・承認、配布先、生成日時、モデルハッシュ
2. エグゼクティブサマリー
   - 総括、最高深刻度、深刻度別件数、確認状態別件数、優先対応、主要制約
3. 診断範囲
   - 案件、対象システム、顧客、診断実施者、期間、方式、許可・拒否 origin、ロール、送信元、上限、除外、前提、禁止操作
4. 対象資産とカバレッジ
   - 資産 ID、FQDN、マスク済み URL、探索・診断 URL 数、委譲ステップ数、観点別の実施状態
5. 評価方法
   - 使用手段、エンジンと版、確認状態の定義、制約の読み方
6. 指摘事項一覧
   - ID、名称、深刻度、確認状態、信頼度、対象、パラメータ、発生数
7. 指摘事項詳細
   - 概要と成立条件、原因（観測事実と推定原因）、再現手順、再現用 Request、観測した Response、レスポンス制御の不足内容、
     診断入力、観測根拠、確認結果、改善策、修正確認条件
8. 改善計画と再診断
   - 優先順位、担当・期限の記入欄、再診断条件、追跡状態
9. 証跡索引
   - 証跡 ID、種類、SHA-256、取得日時、秘匿状態、関連指摘
10. 特記事項
    - 適用範囲、未実施領域、安全性を保証しない旨、問い合わせ先

## 4. 入力と永続化

S07 で `ReportProfile` の各項目を入力する。案件ルートの `report-profile.json` に保存し、
次回の報告書生成時に再利用する。出力は案件の reports ディレクトリへ同じタイムスタンプで保存する。

HTTP 証跡の掲載方法は案件ごとに次から選択する。既定は `relevant` とし、いずれの設定でも
案件証跡に保存した原本は変更しない。

- `relevant`: 短い Body は全文、長い Body は着目語を含む最大6箇所と前後の文脈を掲載する。
- `omit`: 開始行・ステータス行とヘッダーだけを掲載し、Body は省略文字数に置換する。
- `full`: 収集上限内の全文を掲載する。
- `highlightEvidence`: 着目箇所の黄色ハイライトを有効・無効にする。

- `diagnostic-report-<timestamp>.md`: 既存の決定論的 Markdown
- `diagnostic-report-<timestamp>.json`: `AssuranceReportDocument` の構造化データ
- `diagnostic-report-<timestamp>.docx`: 構造化データから直接生成した提出用文書

DOCX は Markdown の変換結果ではない。TypeScript の `docx` ライブラリだけで生成し、Word COM を
実行時依存にしない。

## 5. 視覚仕様

- A4 縦、游ゴシック、黒の本文・見出しを基本とする。
- 表の見出しは濃紺、本文は白と淡青の交互行、細いグレー罫線とする。
- 表紙は余白を広く取り、タイトル、対象名、版、取扱区分を一画面で識別できる構成とする。
- 通常ページには報告書 ID、取扱区分、ページ番号のフッターを付ける。
- 指摘詳細は指摘単位で区切り、表の途中切れと孤立見出しを避ける。
- URLだけが異なる同一現象は1件の指摘へ統合し、URL欄へ全対象URLを1行ずつ列挙する。
  指摘一覧、経営層向け概要、深刻度別・成立状態別の件数も統合後の件数を使用する。
- 統合した指摘でも診断時通信は代表1件へ間引かず、対象URLごとに Request / Response を掲載する。
- Request / Response は等幅フォント、淡灰色の背景、細い罫線で表示し、長い通信はページをまたいで
  継続できる構造とする。
- Request / Response の着目語と、その根拠を要約した「着目箇所」を黄色で強調する。本文に着目語が
  見つからない場合は、通信の開始行を代替の視線誘導として強調する。

## 6. 診断証跡の取扱い

- 対象資産の一覧では URL の userinfo、query 値、fragment を除去または `[redacted]` 化する。
  指摘詳細では再現可能性を優先し、実際の対象 URL、query、fragment を保持する。
- ZAP alert の `messageId` から `core/view/message` を診断run中に取得し、request header/body と
  response header/body を原本証跡へ保存する。取得失敗時は警告を失わず、理由を証跡へ記録する。
- Nuclei は `-include-rr` を使用し、所見の Request / Response を JSONL 原本へ含める。
- 診断時の Cookie、Authorization、Set-Cookie、token、CSRF 値は、脆弱性の再現と判定に必要な
  技術証跡として Request / Response に保持する。報告書を認証情報相当の機密文書として扱い、
  配布先と保管先を案件の承認範囲へ限定する。案件内の原本は改変しない。
- 指摘に対応する実際の Request / Response の一方でも取得できない場合は、提出用 JSON / DOCX / Markdown
  の生成を拒否する。未取得理由、証跡ファイルへのリンク、推測で組み立てた通信を代替表示にしない。
  対象指摘 ID と不足側をエラー表示し、HTTP 証跡を収集できる設定での再診断を要求する。
- Request開始行とResponseステータス行をHTTP形式として検証し、空でない説明文や任意文字列を
  通信証跡として扱わない。
- MarkdownにもDOCX/JSONと同じRequest / Responseを指摘単位で直接埋め込み、証跡IDや
  保存先を通信内容の代替にしない。
- 報告書投影時の同一現象判定は、検出元、engine plugin/template ID（なければ指摘名）、指摘名、
  深刻度、成立状態、HTTP methodを一致条件とする。レスポンスヘッダ・Cookie属性の不足は不足内容が
  同じ場合にURL・query parameterを除外して統合する。入力系の指摘はさらにparameter、攻撃入力、
  観測根拠、説明、Response statusを一致条件とし、URL以外も異なる指摘を誤統合しない。
- 統合は提出用の投影に限定し、案件DBの原所見、原証跡、原finding IDは変更しない。構造化JSONには
  `urls`、`sourceFindingIds`、`technicalEvidenceByUrl`を保持し、証跡索引の関連指摘IDだけを代表IDへ集約する。
- プロファイル値は文字列として正規化し、既定値を明示する。

## 7. 検証ゲート

- `ReportModel` と OpenAPI 契約の整合性テスト。
- 構造化 JSON の指摘詳細に実際の対象 URL と再現用 query が保持されることの単体テスト。
- ZAPの警告とmessage APIの通信が同じ原本証跡へ保存され、指摘ごとに対応付くことの単体テスト。
- Nuclei 実行が Request / Response 同梱オプションを必ず使用することの単体テスト。
- 構造化 JSON / DOCX に指摘ごとの Request / Response が入り、診断時の Cookie・tokenを含む
  再現情報が欠落しないことの単体テスト。
- レスポンスヘッダ欠落の指摘では、不足したヘッダ名が確認結果へ明記されることの単体テスト。
- URLだけが異なる同一のヘッダ欠落4件が1指摘へ統合され、全URLと4組のHTTP証跡をJSON・Markdown・
  DOCXへ保持すること、およびparameter・攻撃入力が異なる入力系指摘を統合しないことの単体テスト。
- 全指摘の構造化JSON・Markdown・DOCXに原因があり、観測事実と推定原因が区別され、脆弱性種別に
  応じた実装・設定上の不備候補を含むことの単体テスト。
- AI文章案が所見ごとに反映され、形式不良・一般論のみ・未知URLを含む案では安全な既定文章へ戻ることの単体テスト。
- Request / Response の一方でも欠落した指摘を含む場合、部分的な報告書ファイルを作らず生成に失敗する
  ことの単体テスト。
- DOCX が有効な ZIP/OOXML として生成され、必要章を含むことの単体テスト。
- A4 レンダリング後に全ページを画像確認し、欠け、重なり、文字化け、表切れ、空白ページを確認する。
- Windows Word でヘッダー、フッター、ページ番号、表組みを確認する。
