# 07 自動探索・ブラウザ 概要設計

対応要件: 仕様書 F08・3.1（認証・フォーム操作・状態遷移を含む自動探索）

## 1. 目的

独立プロファイルのブラウザで、認証・フォーム送信・状態遷移を含む自動探索を行い、
能動診断の対象面を広げる。許可範囲と禁止操作は適用する。AI は任意支援（7章）。

## 2. 再利用する現行資産

- `tools/fast-crawl.js`（高速クローラ）: リンク巡回・robots/sitemap・認証待ち・上限・介入記録
- `tools/crawl-policy.js`: 巡回ポリシー（正規化・除外・認証画面判定）
- `Services/ExplorationPackageBuilder` / `AiInputBuilder`: 実行パッケージ・AI入力の代表パターン化
- `Services/ZcodeExplorationRunner` / `CodexExplorationRunner`: AI画面探索（任意・GLM/Codex）
- Playwright runtime（tools/playwright-runtime）
- document hints（`DocumentHintService`）: 文書由来の追加開始点・優先規則

## 3. 方針の切り替え（現行からの差分）

| 現行 | 本実装 |
|---|---|
| フォーム送信は既定無効・無害な仮値1回 | 認可の許可操作区分（FormSubmit）の内側で、フォーム種別ごとの送信戦略（検索系=代表値、認証系=認証情報（08）、更新系=事前合意時のみ）を適用。禁止語彙・パス・禁止操作リストとの照合を送信前に行う |
| 認証は人が探索ブラウザへ直接ログイン | 自動ログイン（08）を標準とし、SSO/MFAなど自動化できない範囲だけ人の介入（現行の human-intervention.json / resume.signal の仕組みを維持） |
| 巡回はGET中心 | 状態遷移（詳細→一覧、ページャ、タブ）の自動追跡。探索深度・ページ数・通信数は案件上限の内側 |
| 観測のみ | 探索結果を能動診断（10）へ直接接続。探索→採用→診断を Orchestrator の自動計画へ |

## 4. コンポーネント構成

```text
BrowserAdapter（01）: Playwrightワーカーの起動・プロファイル分離・記録（HAR/スクリーンショット）
ExplorationPlanner（新規）: 開始点（StartUrl+document hints）・探索戦略・上限から探索ジョブを計画
FormSubmitPolicy（新規）: フォーム種別判定と送信値の供給（代表値・辞書は05のPayloadSet管理と共通化）
  ※ 探索での送信値は入力例・代表値に限り、攻撃ペイロードは使わない（攻撃は診断ジョブの担当）
InterventionFlow（既存踏襲）: 認証・CAPTCHA等で止まったら介入要求→人が操作→再開
AiExplorationAssist（任意）: Zcode/Codex画面探索を「代表パターン確認」として計画へ差し込める
```

## 5. データモデル

- 観測（ObservedRequest）は現行踏襲。加えて「探索経路」（どのページのどの操作から到達したか）を
  記録し、サイトマップ（03）と診断時計の文脈（操作列）に使う。
- 探索ジョブの記録: 探索戦略・送信したフォーム数と内訳・停止理由・未到達の記録。

## 6. 安全制御と証跡

- すべての巡回・送信は許可Origin・通信数・ページ数・実行時間の内側。禁止語彙検査と警告表示。
- アップロードフォーム・削除系操作は認可の許可操作区分で明示的に許可された場合のみ。
- スクリーンショット・HAR は証跡（20）。ページ内の秘密値は保存時マスクの対象。

## 7. UI / CLI

- 探索画面（現行を発展）: 進行状況・介入要求・探索経路ビュー・観測の代表パターン一覧。
- CLI: `scopepilot explore`（19）＝現行シミュレーションハーネスのフェーズを正式化。
