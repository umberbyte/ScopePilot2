# 21 更新管理 概要設計

対応要件: 仕様書 5章（脆弱性情報と検出ルールの継続更新）・9章（配布と継続保守）

## 1. 目的

ZAP add-on・Nucleiテンプレート・ペイロード集合・辞書・実行環境の版を、取得→検証→固定→
提供の手順で管理する。系列A（A2）ではアプリのリリースで版を固定する。署名付き更新パックと
組織内ミラーは任意拡張（仕様書1.3・5.2）。

## 2. 再利用する現行資産

- `Services/ZapAddonService`: 必須add-onの導入・版・SHA-256の記録と実行時検証
  （zap-environment.json）→ 一般化の種
- `Services/AppSettingsService` の設定保存

## 3. コンポーネント構成

```text
UpdateManager（新規）:
  対象レジストリ: 供給元ごとの更新対象（5.1表）: 汎用ルール(ZAP release)・テンプレート(Nuclei)・
    ペイロード集合(05)・解説辞書・実行環境(Java/Node/Chromium/ZAP/Nuclei)
  手順（5.2）: 確認(24h・手動/オフライン可)→隔離領域へ取得→出典・版・hash・ライセンス記録→
    署名/信頼検証→静的検査（構文・禁止プロトコル・ファイル参照・要求数・スコープ逸脱）→
    fixture回帰→（任意: 署名付きマニフェスト）→実行開始時の版固定
  チャネル: Stable（検証済みrelease）と Review（beta/alpha/利用者作成）。
    実行は既定でStableのみ
  表示（5.4）: 供給元ごとに 最終確認・最終成功・供給元版・審査済み版・使用中版・保留件数・失敗理由。
    「最新」の一語表現は使わない
PayloadSetStore / TemplateStore / RulePackage（05・16・18）: 版・hash・審査状態は本管理に集約
OfflinePack: 別端末で取得した更新パックの読込（改ざん・署名不一致・互換性不一致・旧版差戻し拒否、
  明示的切り戻しは履歴へ）
```

- Nucleiはエンジン側の自動更新を無効化し、製品が固定したローカル集合のみ使用（5.2）。
- CVE情報DB・KEVは任意拡張。採用時は「情報レコード」と実検査結果を分離（5.1）。

## 4. データモデル

- `UpdateRecord`（供給元・版・hash・取得日時・検証結果・審査状態）と `EngineRuntime`（16）。
- 実行記録は使用した版・hashのスナップショットを持つ（6.3）。

## 5. 安全制御と証跡

- 更新用通信は案件通信と分離し、案件URL・Cookie・文書・所見を含めない。
  オンライン照会（OSV等）を選ぶ場合も送信パッケージを明示（5.4）。
- ルールが新たに発生させる通信・操作の審査を省かない。上流追従できない間は保留＋理由表示。
- 実行開始時の版固定・診断途中の更新なし・失敗時の直前検証済み組合せ保持（5.2手順8）。

## 6. UI / CLI

- 「更新と実行環境」画面: 供給元一覧・状態・保留理由・オフライン指定・パック読込。
- CLI: `scopepilot update check|apply|export-pack|import-pack`。

## 7. 未解決事項（A2）
