# GO-15 Advanced Fuzzer implementation (2026-11-10)

Reference: `advanced-mode-redesign/docs/design/40-advanced-mode-redesign.md`, P4 / A32 (read from the sibling worktree). Existing A07 route and screen remain reachable; no navigation redesign, OTP/SAML, packaging, push, or Linear changes.

## Behavior

- Replaced name/value comma syntax with query parameter detection and per-position payload controls. The body editor supports text selection followed by Add body insertion, represented by paired section-sign markers. Supports GET/POST/PUT/PATCH/DELETE and a content type; body positions use raw replacement, query positions use URLSearchParams encoding. Removing a body position keeps its original marked value. Repeated query names are replaced together, as explained in the screen.
- Supports Sniper (preserves inactive originals), Battering ram (first position set for all positions), Pitchfork (shortest set), and Cluster bomb. UI defaults to Sniper; omitted API strategy retains the existing Cartesian behavior for CLI compatibility.
- Registered payload sets can be selected per position and are resolved by the core catalog. Source/version/license/hash appear in the selection area. New manual registrations compute SHA-256 from UTF-8 JSON values rather than sending `manual-entry`. Direct input preserves whitespace and empty values. Jobs snapshot position/source/version and the SHA-256 of the actual selected values. No exploit payload catalog was added.
- Added shared TypeScript contracts and OpenAPI routes: GET status, POST/GET jobs, POST stop under `/api/fuzzer`. Existing synchronous runs API and cluster output remain compatible.
- Nonblocking job acceptance, polling progress, partial results, and cooperative stop. A stop during rate waiting is rechecked before sending. An in-flight HTTP request may finish; no subsequent request is started. Validation failures appear as Failed jobs, and combinations exceeding the cap produce no sends.
- Per-result payload/status/byte length/time/length delta/body-status difference; changed-only filtering and hash/cluster details. Differences compare against the first result and are explicitly not vulnerability verdicts.
- Fixture transport is identified before starting and in run progress. Its responses are deterministic, durations are simulated as zero, and it sends no target HTTP traffic. Product engine composition remains unchanged.
- Caps are bounded by the case request limit and an absolute 10,000-result ceiling; the default is 200. Rate is 1-2 RPS (default 2), concurrency remains one. Scope, case identity, current request limit and case duration are checked before each send. Redirect following remains disabled. Existing role cookie filtering and secret-value exclusion from result metadata remain intact.

## Limits

Fuzzer jobs are local in-memory operations: one active asynchronous Fuzzer job, last 20 job views retained, no restart/resume claim. This branch does not yet provide the redesign's shared JobRegistry/SSE infrastructure, so Fuzzer uses its own typed polling API. The existing synchronous endpoint remains available to CLI callers.

HTTP responses retain bounded length/hash metadata, not raw response bodies; details show hashes/clusters. Arbitrary raw headers/cookie insertion editing, processor pipelines beyond query encoding, response-text match conditions, persistent job history, and full A92 library management are outside this GO-15 implementation. Existing session-role cookies remain supported. These broader A32/P4 items are not claimed as implemented.

No diagnostic benchmark or remote target scan was run; HTTP transport tests use local loopback servers and generic fixture values only. Changes remain local and uncommitted; no push and no Linear mutation.
