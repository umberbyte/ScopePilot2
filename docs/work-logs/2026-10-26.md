# 2026-10-26 ワークフロー診断の TypeScript 移植（DVWA 18分類）

## 目的

旧 C# 実装（main ブランチ `Services/WorkflowScan/**`、2026-10-25 の作業ログ参照）の
ワークフロー診断を本リポジトリ（TypeScript/Electron）へ移植する。ユーザーの明示依頼に
よる実装であり、AGENTS.md「ベンチマークについて」節のとおり検証対象専用処理として
 ペイロード集合の版を結果へ記録する。

## 実装

- `packages/core/src/domain/workflow-scan.ts` — 21種のチェックとオーケストレーション。
  HTTP 実行は `WorkflowScanTransport` 契約（輸送ポート）越しに行い、core は送信内容の
  組み立てのみ担う（design/22: ScopePilot 自身の送信は送信前制御可能な経路）。
  - 認証系: ブルートフォース対策 (CWE-307)、CSRFパスワード変更 (CWE-352)、
    ファイルアップロードと実行 (CWE-434)、CAPTCHA迂回 (CWE-602/489)。
  - セッション・制御: セッションID生成規則の特定（連番・時刻・連番MD5、CWE-330）、
    CSP許可元とスクリプト取込み (CWE-693)、クライアント側トークン生成の再現 (CWE-602)。
  - XSS・インジェクション: 反射型・格納型・DOM型 (CWE-79)、API経由のOSコマンド
    インジェクション（echo 出力と true/false 終了コードオラクルの2戦略、CWE-78）、
    SQLインジェクションのURL単位成立確認（引用符・数値ペイロード×GET/POST、CWE-89）、
    LFI（絶対パス・トラバーサル・`....//` 再構成・`file://`・php フィルタ、CWE-98/22）。
  - 暗号: 反復XORの既知平文からの鍵回収 (CWE-327/321)、AES-ECBトークンのブロック
    組み替えによる管理者偽造 (CWE-327)、CBCパディングオラクルによる平文回収 (CWE-203)。
  - 認可・API: メニュー外APIでの全利用者データ取得と他利用者情報の書換え (CWE-862/639)、
    アクセスログ画面の無保護な公開 (CWE-862)、廃止APIの機微情報 (CWE-200)、
    マスアサインメント (CWE-915)、オープンリダイレクト low/medium/high (CWE-601)。
  - オーケストレーション: ログイン、security.php によるレベル切替え
    （low→medium→high、終了後に元レベルへ復元）、 AbortSignal、要求上限。
  - 破壊的検証（パスワード・権限）は実施後に元の値へ復元し、復元成否を応答テキストまたは
    別セッション（probe 輸送）でのログイン検証で確認する。reCAPTCHAキー未設定のDVWAは
    結果表示を警告で置き換えるが変更自体は実行されるため、効果検証が必須。
- `packages/adapters/src/workflow-scan-transport.ts` — `NodeWorkflowScanTransport`。
  Node fetch（手動リダイレクト）で動き、Cookie 管理・baseUrl Origin 固定（送信前 scope
  強制）・要求上限・証跡ログ（パスワード等の伏せ字、クエリ・リダイレクト先含む）を担う。
- `packages/adapters/test/fake-dvwa-server.ts` + `workflow-scan.test.ts` — DVWA互換の
  インプロセスサーバー（18分類の脆弱挙動と high/impossible の保護挙動、実DVWAと同一の
  暗号仕様、CAPTCHA無表示変更の再現）と回帰テスト。全チェックID検出・レベル別暗号判定・
  パスワードとレベルの復元・ログイン失敗時の安全な完了・証跡への秘密値非露出・純粋関数群を検証する。

## シンプルモード統合

- `BaselineFlowService` の確認済み実行計画へ `workflow-scan` ステップを追加した。認証済みで
  `/vulnerabilities/` 配下の対象を選んだシンプルモードでは、21チェックを自動で計画へ含める。
- ZAP・Nuclei・workflow scan の要求上限は計画全体の上限内で分割する。workflow scan 本体と
  復元確認用probeは共有カウンターを使い、Origin固定・中断・要求上限を同じ制御下に置く。
- シンプルモードのログイン資格情報はサービスのメモリ内だけに保持し、API応答・監査イベント・
  SQLite証跡へ値を出さない。通信証跡では元の秘密値に加え、password・CSRF token等も伏せ字化する。
- 検出結果は `observation` 所見としてFinding台帳へ取り込み、チェックID・security level・URL・
  parameterで重複排除する。診断時Request/Responseを所見に対応付けて保存するため、S07の提出用
  Markdown・DOCX・構造化JSONでもHTTP証跡の完全性ゲートを通過できる。
- S05には21チェック、payload版、Origin、要求上限を含む計画ステップを表示し、S06には実行中ログ、
  21種中の検出種類数、所見数、要求数、失敗時の独立エラーを表示する。
- `workflow-scan-simple-flow.test.ts` で Simpleログイン→確認計画→ZAP→21チェック→Finding取込→
  専用診断経路更新→秘密値伏せ字→パスワードとsecurity level復元をFake DVWAに対して縦断検証した。

## 汎用ペイロードカタログ v2

- `@scopepilot2/payloads` を新設し、DVWA固有URLから分離した、版管理可能な静的ペイロードカタログを追加した。
  カタログ参照は `scopepilot-workflow-payloads/v2.0.0` と正規化JSONの SHA-256 を組み合わせ、
  診断結果・証跡から利用した内容を一意に追跡できる。
- ペイロードは capability、入力context、対象platform、oracle、tags、安全性属性で選択する。
  状態変更・成果物生成・遅延・残留物には、確認、復元、最大試行数、最大遅延、後始末の制約を必須化した。
- 実行時にカタログ全体を検証し、動的生成カタログ、重複ID、不正なペア、テンプレート変数のずれ、
  安全性属性の欠落を拒否する。実行時AIによる攻撃コード生成は行わない。
- 既存のworkflow scanでは、認証試行、SQL boolean differential、API command injectionの入力を
  カタログ参照へ置き換えた。要求上限、Origin固定、復元処理など既存の実行制御は維持する。
- `payload-catalog.schema.json` と単体テストを追加し、カタログの識別、選択、レンダリング、
  安全性検証、ペア整合性、残留物の後始末要件を確認した。
- シンプルモードのS05では、workflow-scan stepが使うカタログID・版・SHA-256を明示する。
  カタログ参照はstepの`engineVersion`として計画ハッシュへ含まれるため、確認後の差替えは計画不一致になる。
- S06の完了要約にも実行時のカタログ参照を表示し、同じ値をworkflow結果・所見のengine version・
  HTTP証跡へ保存する。縦断テストで計画、結果、証跡の参照一致を確認した。

## 診断報告書の二部構成化

- 第一部を意思決定・対応用サマリーとし、検証レベル別の重複を脆弱性系統単位へ統合する。
  各系統には、任意コード実行、他人へのなりすまし、認証なしの機能利用など、攻撃者が具体的に
  何をできるかを記載し、成立確認済みか候補（要確認）かを明確に分離する。
- 第二部を技術証跡別冊とし、全URL、全HTTP Request/Response、観測根拠、再現手順、原因、対策、
  修正確認基準、証跡索引を従来どおり省略せず保持する。第一部から第二部の指摘IDへ追跡できる。
- 通常の報告書生成で、第一部、第二部、Markdown、構造化JSON、各成果物のSHA-256を持つ
  マニフェストを同時に保存する。S07から第一部・第二部・マニフェストを個別に開ける。
- 最後の診断結果から実生成し、第一部は35系統を9ページに収録した。第二部は54指摘・132元指摘・
  113証跡を保持する。

### 二部構成報告書の検証

- `npm test`: 全ワークスペース合格（既存の環境依存スキップを除く）。
- Microsoft Wordで第一部の全9ページをレンダリングし、文字切れ、列欠落、空白ページがないことを確認した。

## 第二部のHTML索引化

- 大量の技術証跡を参照しやすくするため、第二部の出力をDOCXから単一HTMLへ変更した。第一部DOCX、
  Markdown、構造化JSON、成果物マニフェストは維持する。
- 第二部には章別・指摘別の固定ナビゲーション、指摘ID・名称の検索、指摘索引、各指摘とURL別HTTP証跡、
  証拠原本索引へのアンカーを追加した。本文をスクロールしてもナビゲーションは常に表示される。
- HTMLは外部資産へ依存せず、値をHTMLエスケープし、診断時のRequest/Responseと着目箇所の強調を保持する。
